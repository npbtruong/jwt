01 · Định tuyến

api.php vs web.php

Từ Laravel 11+, chỉ có web.php mặc định. API là tuỳ chọn — chạy php artisan install:api hoặc tự thêm. Khác biệt thật không phải HTML/JSON, mà là middleware & cách giữ trạng thái.

STATEFUL  Có session + cookie + CSRF. Trình duyệt tự mang cookie. Hợp web truyền thống & SPA cùng domain (Sanctum).

// prefix: (không) — /profile
Route::get('/profile', fn() => view('profile'));

STATELESS  Không session, không CSRF. Client tự mang token mỗi request. Hợp mobile, microservice, khác domain.

// prefix: /api — /api/users
Route::get('/users', fn() => User::all());
Nhớ: đặt route API trong web.php để dùng session-auth cho SPA cùng domain không sai — đó là pattern Sanctum khuyến nghị. Chọn file = chọn bộ middleware, không phải chọn đúng/sai.
02 · Xác thực

Ba cách trả lời “ai đang gọi?”

Session & JWT trả lời “giữ trạng thái ở đâu”. OAuth2 trả lời “ai được phép cấp token” — khác tầng, không mâu thuẫn.

03 · JWT

Giải phẫu một JWT (HS256)

JWT là ba đoạn base64url nối bằng dấu chấm. Bấm vào từng đoạn để xem bên trong.

eyJ0eXAiOiJKV1QiLCJhbGciOiJIUzI1NiJ9.eyJzdWIiOiJib29raW5nX2NvbSIsImV4cCI6MTc4NH0.yHhEKAmxYF29RZSlxB-HUPhsElSPrYj2TVaF8Er 
// Bấm một đoạn màu ở trên để xem chi tiết…

Header

Loại token + thuật toán ký (alg: HS256).

Payload

Các claim: sub, exp, iat… Không mã hoá — ai cũng đọc được.

Signature

HMAC-SHA256(header.payload, secret). Chống sửa payload.

Ký (issue) 
sig = base64url(
  hmac_sha256(
    "header.payload", secret
  ))
Verify (middleware) 
// 1. tính lại sig, so sánh
hash_equals(sig, expected)
// 2. check exp còn hạn?
// 3. resolve client theo sub
Payload không phải bí mật. Đừng bỏ mật khẩu/dữ liệu nhạy cảm vào JWT — nó chỉ được ký, không được mã hoá. Chữ ký chỉ đảm bảo không bị sửa, không giấu nội dung.
04 · Kiến trúc

Toàn cảnh một webhook microservice

Booking.com gọi 2 endpoint: lấy token, rồi bắn webhook. Bên trong là chuỗi 6 bước — chú ý màu: Redis chặn trùng, MySQL lưu, Worker gửi mail.

Booking
APOST /oauth/token — gửi client_id + secret → nhận JWT ngắn hạn (verify secret đã hash).
Booking
BPOST /webhook + Authorization: Bearer <jwt> + JSON reservation.
API
1JwtMiddleware: verify chữ ký + hạn, resolve client, gắn vào request. Sai → 401.
Redis
2SET event_id NX EX — chặn trùng nguyên tử. Đã tồn tại → 200 “already processed”, dừng.
MySQL
3Transaction: upsert reservation theo event_id. Xong trước khi trả lời.
Queue
4dispatch job ->afterCommit() lên queue notifications — chỉ chạy nếu commit thành công.
API
5Trả 200 ngay với envelope thành công. Việc chậm (mail) đã đẩy sang queue.
Worker
6Container riêng queue:work gửi mail. Lỗi → retry $backoff → cuối cùng vào failed_jobs + log.
Nguyên tắc vàng: việc quan trọng & nhanh (lưu DB) làm đồng bộ trước khi trả lời; việc chậm & chịu lỗi được (gửi mail) làm bất đồng bộ trên worker.
05 · Idempotency

event_id & chống xử lý trùng

Webhook là at-least-once: OTA đảm bảo gửi ít nhất 1 lần, không phải đúng 1 lần. Mạng lỗi / timeout → nó gửi lại cùng event_id. Không chặn → lưu trùng + gửi mail 2-3 lần.

Cuộc đua: 2 request cùng event_id tới cùng lúc
Request #1
SET … NX
✓ set được → xử lý
REDIS
SET NX EX
(nguyên tử)
Request #2
SET … NX
✗ key đã có → 200 dừng

Vì SET NX là một thao tác nguyên tử, dù hai request chạy song song, chỉ đúng một nhận được “set OK”. Không thể cả hai cùng thắng.

Lớp 1 — Redis

SET idem:webhook:evt_9f8… 1
    EX 86400 NX

Nhanh, chặn trước. TTL > cửa sổ retry của OTA.

Lớp 2 — Database

$table->string('event_id')
       ->unique();

Chắc chắn. Redis bị xoá sạch, DB vẫn chặn insert trùng.

Defense in depth: Redis lo tốc độ, unique index lo tính chắc chắn. Đừng nhầm event_id (mã sự kiện webhook) với ota_reservation_id (mã booking) hay reservation_id (id trong DB của bạn).
06 · Sync / Async

Ghi đồng bộ · gửi mail bất đồng bộ

Điểm tinh tế nhất: dispatch()->afterCommit() đặt bên trong transaction. Job chỉ được đẩy vào Redis sau khi commit — nếu transaction rollback, mail không bao giờ gửi.

DB::transaction(function () use ($payload) {
    $reservation = $this->reservations->upsertByEventId($row);  // (1) lưu — SYNC

    SendReservationNotificationJob::dispatch($reservation)
        ->afterCommit();   // (2) chỉ đẩy queue SAU khi commit

    return $reservation;
});
// (3) trả 200 ngay — mail chạy off-request trên worker
Vì sao afterCommit quan trọng? Không có nó, job có thể chạy trước khi row kịp commit → worker query DB không thấy reservation → lỗi. afterCommit đồng bộ hai thế giới: DB & queue.

--sleep=1 chỉ áp dụng khi queue rỗng. Nhiều job liên tiếp thì worker xử lý hết cái này sang cái kia, không ngủ. Thất bại hết $tries lần → vào failed_jobs + failed() ghi log có cấu trúc.
08 · Hợp đồng & tầng

Envelope nhất quán + kiến trúc phân tầng

Một ApiResponse helper + một exception Handler tạo ra cùng một hình dạng JSON cho mọi path. Consumer phụ thuộc vào nó — đó là interface ổn định của service.

success 
{
  "success": true,
  "message": "Reservation received",
  "data": { "reservation_id": 12 }
}
error 
{
  "success": false,
  "message": "The given data…",
  "errors": { "…check_in": ["required"] }
}
Luồng đi qua các tầng (mỗi tầng một việc)

Request → Middleware verify JWT → Controller thin → Service business logic → Repository DB / Store Redis → ApiResponse

Controller mỏng: validate → gọi service → trả envelope. Không business logic, không Redis:: thô trong controller. Mọi phụ thuộc tiêm qua interface → thay Redis/DB không đụng caller.
09 · Recipe

Checklist: tự dựng một webhook

Bấm để đánh dấu hoàn thành. Đây là công thức rút gọn cho lần sau.

0 / 12
  • ✓01Tách route — api.php, prefix /v1, throttle theo config.
  • ✓02Phát token — client gửi id+secret; verify secret đã hash; ký JWT ngắn hạn.
  • ✓03Middleware verify — kiểm chữ ký + hạn, resolve client, gắn vào request.
  • ✓04Validate payload — FormRequest, kể cả field lồng reservation.*.
  • ✓05Idempotency — Redis SET event_id NX EX + unique index ở DB.
  • ✓06Persist — transaction, upsert theo event_id, xong trước khi trả lời.
  • ✓07Dispatch — job ->afterCommit() lên named queue.
  • ✓08Respond — trả 200 + envelope ngay lập tức.
  • ✓09Worker riêng — queue:work redis --queue=…, container scale độc lập.
  • ✓10Xử lý lỗi — $tries/$backoff, failed_jobs, log có cấu trúc.
  • ✓11Config-driven — TTL, tries, rate limit, idempotency TTL trong env.
  • ✓12Stateless — không giữ state trong app → scale worker + app sau LB.
Ghi sync · gửi async · chặn trùng nguyên tử · hợp đồng ổn định — bốn trụ của một webhook đáng tin.
